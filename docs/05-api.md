# 05 — API Reference

Base URL (dev): `http://localhost:8000`. Interactive docs at `/docs` (Swagger,
auto-generated by FastAPI).

## Phase 0

### `GET /health`
Liveness check.
```json
{ "status": "ok", "service": "noacf-api", "version": "0.7.0" }
```

## Phase 1

All auth endpoints are server-mediated (D9): the client only talks to
FastAPI; the server uses the Supabase service-role key. Signup/login return
a Supabase JWT that the client sends as `Authorization: Bearer <jwt>`.

### `POST /auth/signup`
```json
→ {"email": "a@b.com", "password": "min8chars", "display_name": "Kiwi"}
← 200 {"access_token": "<jwt>", "user": {"id": "...", "email": "...", "display_name": "Kiwi"}}
```
Creates the Supabase Auth user (auto-confirmed in dev — no SMTP configured)
and the `public.users` profile row, then logs in and returns the session.

### `POST /auth/login`
```json
→ {"email": "a@b.com", "password": "..."}
← 200 {"access_token": "<jwt>", "user": {...}}
← 401 {"detail": "Invalid email or password"}
```

### `POST /auth/forgot-password`
```json
→ {"email": "a@b.com"}
← 200 {"message": "If that email exists, a reset link has been sent."}
```
Same response whether or not the account exists (no user enumeration).
Requires SMTP configured in Supabase to actually deliver.

### `GET /auth/me`
```json
← 200 {"id": "...", "email": "...", "display_name": "Kiwi"}
← 401 {"detail": "Invalid or expired token"}
```
Self-heals the `public.users` profile row if it is missing.

### `POST /auth/change-password` (added Phase 2, auth required)
```json
→ {"current_password": "...", "new_password": "min8chars"}
← 200 {"ok": true}
← 400 {"detail": "Current password is incorrect"}
```
Verifies the current password (via a sign-in attempt) before updating.

## Phase 2

TMDB access is server-side only (`server/app/tmdb.py`) so the API key never
reaches the client; the `films` table caches fetched metadata. `poster_url`
values are absolute URLs against the TMDB image CDN.

### `GET /films/search?q=`
```json
← 200 {"results": [{"tmdb_id": 329865, "title": "Arrival", "year": 2016,
                    "poster_url": "https://image.tmdb.org/t/p/w342/…", "overview": "…"}]}
```
Top 8 TMDB results.

### `GET /films/tmdb/{tmdb_id}`
```json
← 200 {"tmdb_id": 329865, "title": "Arrival", "year": 2016,
       "genres": ["Drama", "Science Fiction", "Mystery"], "runtime": 116,
       "overview": "…", "poster_url": "…",
       "in_library": {"id": "…", "status": "watched", "rating": 4.5} | null}
← 404 {"detail": "Film not found on TMDB"}
```

### `GET /films/mine?status=watched|watchlist&limit=250&offset=0`
```json
← 200 {"films": [{"id": "<user_film id>", "film_id": "…", "tmdb_id": 329865,
                  "title": "Arrival", "year": 2016, "genres": ["Drama", …],
                  "runtime": 116, "poster_url": "…",
                  "status": "watched", "source": "manual|letterboxd",
                  "rating": 4.5 | null, "watched_on": "2026-10-20" | null,
                  "added_at": "…"}],
       "total": 1600, "limit": 250, "offset": 0}
```
Ordered by `added_at` desc; optional `status` filter. `limit` is 1–500
(default 250), `offset` is zero-based, and `total` is the full filtered count.
The client follows pages until all rows are loaded, avoiding PostgREST's
default 1,000-row truncation.

### `POST /films/mine`
```json
→ {"tmdb_id": 329865, "status": "watched", "rating": 4.5, "watched_on": "2026-10-20"}
← 201 {<user_film row + film fields>}
```
`rating`/`watched_on` optional. Fetches + caches TMDB metadata on first sight
of a film; upserts on `unique(user_id, film_id)` so re-adding updates status.

### `PATCH /films/mine/{user_film_id}`
```json
→ {"status": "watchlist", "rating": 4.0, "watched_on": "2026-10-20"}   (any subset)
← 200 {"ok": true}   ← 404 if the row is not the caller's
```

### `DELETE /films/mine/{user_film_id}`
```json
← 200 {"ok": true}   ← 404 if the row is not the caller's
```

### `POST /import/letterboxd` (multipart form, field `file`)
```json
← 202 {"import_id": "…", "status": "queued", "total_rows": 1600}
← 400 {"detail": "Not a Letterboxd export CSV — …"}
```
Accepts `diary.csv`, `ratings.csv`, `watched.csv`, `watchlist.csv` (any file
with `Name`+`Year` columns). The request only validates/normalizes the CSV and
creates a persistent job; a background worker processes 20-row batches with
checkpoints. Status is `watchlist` when the filename contains "watchlist",
otherwise `watched`. Only name/year/rating/watched date are retained for resume.
Matching remains catalogue-first, then TMDB title+year (title-only fallback).
TMDB 429/network/upstream failures receive at most four attempts with bounded
exponential backoff and jitter; one film's failure does not stop remaining rows.

### `GET /import/{import_id}`
```json
← 200 {"id": "…", "status": "processing|completed|completed_with_errors|failed",
       "total_rows": 1600, "processed_rows": 800,
       "added": 700, "updated": 20, "duplicates": 50,
       "unmatched_count": 10, "failed": 20, "next_row": 800,
       "error": null, "created_at": "…", "updated_at": "…", "completed_at": null,
       "unmatched": [{"row": 42, "name": "Notarealfilm Xyzqw", "year": 2099}],
       "failures": [{"row": 84, "name": "Arrival", "year": 2016,
                     "error": "502: TMDB rate limited after retries"}]}
← 404 {"detail": "Import job not found"}
```
Owner-scoped. `duplicates` covers repeat CSV rows and already-current library
rows; `failed` means retryable temporary failures, not unmatched titles. The
stored CSV payload and internal result map are never exposed.

#### Letterboxd count semantics and remaining limitations
The count investigation against the import worker established:
- `total_rows` is the number of normalized CSV data rows with a non-empty
  `Name`; the header and blank-name rows are excluded, while duplicate film rows
  remain countable work.
- `processed_rows` is the number of stored row outcomes after resume-aware
  adjustment. At a terminal state it should equal
  `added + updated + duplicates + unmatched + failed`.
- `duplicates` includes both repeated rows inside the CSV and rows that already
  matched the current library state, so it is not a measure of unique films.
- `failed` rows remain resumable; successful rows are not intentionally
  rematched. A resume temporarily decrements a failed row before recording its
  replacement outcome.

Remaining limitations: title+year matching can still choose the wrong TMDB
result; there is no manual match-review queue; target status is inferred from
the filename (`watchlist` substring); the original CSV is deliberately not
retained; and workers are per-process daemon threads, so multi-worker import
execution would require a real queue/locking strategy.

### `POST /import/{import_id}/resume`
```json
← 202 {<job queued for resume>}
← 409 {"detail": "Import is already processing"}
```
Retries pending and failed rows from the last checkpoint; successful rows are
not intentionally rematched. Upserts on `unique(user_id, film_id)` make repeat
imports and resume idempotent. Fresh `processing` jobs return 409; stale ones
may be resumed. Queued/processing jobs are also recovered on server startup.

## Phase 3

Reflection and discovery chat. `LLM_PROVIDER=mock` selects the deterministic
provider (no API key); every user and assistant message, including the opening,
is stored verbatim in `messages` (D11). All routes require auth and are scoped
to the caller. A conversation's `film` is `null` or contains
`id/tmdb_id/title/year/genres/runtime/overview/poster_url`.

### `POST /conversations`
```json
→ {"type": "reflection", "tmdb_id": 329865, "watch_type": "seen"}
← 201 {"conversation": {"id": "…", "type": "reflection", "status": "active",
       "watch_type": "seen", "title": "Reflection on Arrival",
       "created_at": "…", "updated_at": "…", "ended_at": null, "film": {...}},
       "messages": [{"id": "…", "role": "assistant", "content": "…",
                     "metadata": {"kind": "opening"}, "created_at": "…"}]}
```
Use `film_id` for an existing catalogue row or `tmdb_id` to fetch/cache it.
`type` defaults to `reflection`; `watch_type` is optional `seen|planning` but
requires a film (400 otherwise). For a film-free prompt reflection send
`{"type":"reflection","title":"What film character would you want as a friend?"}`.
The response includes the persisted assistant opening.

### `GET /conversations?status=active|completed&type=reflection|discovery`
```json
← 200 {"conversations": [{<conversation with film>}…]}
```
Ordered by `updated_at` desc; both filters are optional.

### `GET /conversations/{id}`
```json
← 200 {"conversation": {<conversation with film>},
       "messages": [{"id": "…", "role": "assistant|user",
                     "content": "…", "metadata": {}, "created_at": "…"}…]}
← 404 {"detail": "Conversation not found"}
```
Messages are chronological. Full history is returned for display; only the LLM
context is bounded (last 12 messages + 5 confirmed memories by default).

### `POST /conversations/{id}/messages`
```json
→ {"content": "I loved the quiet atmosphere and the way it handled grief."}
← 201 {"user_message": {<stored message>}, "assistant_message": {<stored message>}}
← 409 {"detail": "This conversation has ended"}
```
Stores the user message verbatim, assembles bounded context, generates and
stores the assistant reply, and touches the conversation's `updated_at`.
Content is required (1–4000 chars).

## Phase 4

Guided insight review (F3/D12). A **memory review item** has this stable shape:

```json
{
  "id": "…",
  "conversation_id": "…",
  "content": "You kept returning to quiet and family in this reflection.",
  "kind": "theme",
  "status": "proposed",
  "explanation": "Proposed because this idea appears in more than one of your messages.",
  "source_message_ids": ["…"],
  "source_messages": [{"id": "…", "role": "user", "content": "…", "created_at": "…"}],
  "created_at": "…",
  "updated_at": "…"
}
```

`conversation_id` is derived by resolving `source_message_ids` to owned,
append-only messages; no parallel insight/profile table exists. Extraction sees
the same bounded recent-message window as chat (F4), never full history or
proposed/rejected memories. Provider output is validated before insert; invalid
items are discarded. The deterministic mock returns at most three proposals.

### `POST /conversations/{id}/end`
```json
→ (no body)
← 200 {"conversation": {<conversation, status="completed", ended_at="…">},
       "proposed_memories": [{<memory review item>}…]}
← 404 {"detail": "Conversation not found"}
← 422 {"detail": [{"type": "uuid_parsing", …}]}
← 502 {"detail": "Insight extraction failed; the reflection was not ended"}
```
Validates ownership and state, sets `status`/`ended_at`, and leaves every stored
message unchanged. First completion creates only `status="proposed"` memories.
A repeat call performs no extraction and returns the same linked review rows in
their current `proposed|confirmed|rejected` states; the field name remains
`proposed_memories` for contract stability. Ending a reflection with no
substantive user messages returns an empty list.

### `GET /conversations/{id}/memories`
```json
← 200 {"memories": [{<memory review item>}…]}
← 404 {"detail": "Conversation not found"}
```
Returns all review rows linked to one owned reflection, across all statuses,
with only the cited source messages (never the full conversation as debug
context).

### `DELETE /conversations/{id}` (auth required)
```json
← 200 {"deleted": true}
← 404 {"detail": "Conversation not found"}
```
Deletes an owned reflection (or any own conversation) and everything derived
from it: first the `memories` rows whose `source_message_ids` reference its
messages (any kind, any status — proposed, confirmed, or rejected), then the
messages, then the conversation row. The recommendation cache for the user is
invalidated because rankings are built from confirmed memories. This keeps
deleting a reflection from leaving orphaned insights behind in My Profile.

### `GET /memories?status=proposed|confirmed|rejected`
```json
← 200 {"memories": [{<memory review item>}…]}
← 422 {"detail": [{"type": "literal_error", …}]}
```
Owner-scoped; the status filter is optional. Ordered by `updated_at` desc.

### `PATCH /memories/{id}`
```json
→ {"status": "confirmed"}
→ {"status": "confirmed", "content": "Edited wording chosen by the user"}
→ {"status": "rejected"}
← 200 {"memory": {<memory review item>}}
← 400 {"detail": "Nothing to update — provide edited content"}
← 404 {"detail": "Memory not found"}
← 409 {"detail": "Rejected memories cannot be changed"}
```
Valid transitions (D12/D29): `proposed → confirmed` (optionally edited),
`proposed → rejected`, `confirmed → confirmed` (re-edit wording; a no-content
no-op returns 400), and `confirmed → rejected` (retraction from My Profile).
`rejected` is terminal (409). Edit-and-keep updates `content` and `status`
together; `source_message_ids` and source messages are always preserved.
Rejecting with edited content, blank content, malformed UUIDs, or a status
outside the contract returns 422. Cross-user access is 404.

## Phase 5

### `GET /profile/summary` (auth required)
```json
← 200 {
  "display_name": "Cheri",
  "stats": {
    "films_watched": 247, "watchlist": 12,
    "confirmed_insights": 5, "proposed_awaiting_review": 2,
    "reflections_completed": 3,
    "top_genres": [{"genre": "Drama", "count": 41}, …],
    "genre_counts": [{"genre": "Drama", "count": 41}, …]
  },
  "summary": "Cheri's reflective profile draws on 5 confirmed insights…",
  "groups": {
    "theme": [{<memory review item>}…],
    "preference": [{<memory review item>}…],
    "insight": [{<memory review item>}…]
  }
}
← 401 {"detail": "…"}
```
The reflective profile (F2). Built ONLY from `confirmed` memories (D12):
`summary` is a deterministic, human-readable paragraph (no LLM call) and is
`null` when nothing is confirmed yet; `groups` contains the confirmed memories
grouped by `kind`, each with `source_messages` and `source_reflection`
attribution ("from your reflection on <film>, <date>"). `top_genres` is genre
frequency across watched films (top 3, for the summary sentence and the
overview pills); `genre_counts` is the same frequency with no limit, powering
the profile's Genres tab. Stats use exact server-side counts.

### `POST /auth/onboarding-complete` (auth required)
```json
→ (no body)
← 200 {"id": "…", "email": "…", "display_name": "…", "onboarding_completed": true}
```
Marks the onboarding flow finished. Only the Letterboxd import step is
skippable; the client requires the film picks, first reflection and
questionnaire before calling this.
`onboarding_completed` is also returned by `POST /auth/signup`,
`POST /auth/login` and `GET /auth/me`; new signups default to `false`
(migration 0004, D30).

### Phase 2 contracts extended in Phase 5
- `GET /films/mine` now returns `{"films": […], "total", "limit", "offset",
  "counts": {"all", "watched", "watchlist"}}` — exact per-status totals for the
  My Films header and filter pills, independent of pagination.
- `POST /films/mine` and Letterboxd imports implement watched-wins (D28): an
  existing `watched` row is never downgraded to `watchlist`; a `watchlist`
  row is upgraded to `watched` by any watched signal.

## Phase 6

Deterministic recommendation engine (D35) — no LLM or embeddings involved;
the only external calls are TMDB list endpoints. Results are cached per user
for 5 minutes; feedback posts and style changes invalidate the cache.

### `GET /recommendations?limit=12` (auth required, limit 1–24)
```json
← 200 {"recommendations": [{
  "tmdb_id": 693134, "title": "Dune: Part Two", "year": 2024,
  "genres": ["Science Fiction", "Adventure"], "poster_url": "https://…",
  "score": 4.31,
  "why": "Because you rated \"Arrival\" 5★ and it matches your insight: You love quiet, hopeful sci-fi stories.",
  "source_memories": ["You love quiet, hopeful sci-fi stories."]
}]}
```
Seeds are explicit "more like this" feedback, then ≥4★ rated and watchlisted
library films; each seed pulls TMDB recommendations and a `/discover` pool
covers the library's top genres. Library films and "not for me" films are
always excluded. Every card carries a human-readable `why` plus the confirmed
memories it matched (`source_memories`, capped at 3). An empty library returns
popular TMDB picks with an honest cold-start why-line.

### `POST /recommendations/feedback` (auth required)
```json
→ {"tmdb_id": 693134, "signal": "more_like_this", "title": "Dune: Part Two"}
← 200 {"tmdb_id": 693134, "signal": "more_like_this"}
→ {"tmdb_id": 693134, "signal": "love_it"} → 422
```
Upsert on `unique(user_id, tmdb_id)` (D36): repeating a signal updates the
row. `not_for_me` becomes a hard exclusion; `more_like_this` becomes the
strongest seed on the next run. `title` is denormalised so why-lines never
need an extra TMDB call.

### `DELETE /recommendations/feedback/{tmdb_id}` (auth required)
```json
← 200 {"tmdb_id": 693134, "signal": null}
```

### `GET /profile/preferences` (auth required)
```json
← 200 {"recommendation_style": 30}
```

### `PATCH /profile/preferences` (auth required)
```json
→ {"recommendation_style": 85}
← 200 {"recommendation_style": 85}
→ {"recommendation_style": 150} → 422
```
The Settings "More niche ↔ Mainstream" slider (N6, D37). 0 = most niche,
100 = most mainstream; it scales a popularity term (TMDB `vote_count`) in the
scoring formula, on top of the always-on taste/insight grounding.

### `POST /profile/questionnaire` (auth required)
```json
→ {"answers": [{"question": "What kinds of stories do you keep coming back to?",
                "answer": "Quiet science fiction about memory and loss."}]}
← 201 {"saved": 1}
→ {"answers": [{"question": "Q", "answer": "<501 chars>"}]} → 422
```
The onboarding about-you questionnaire (D38). Each non-blank answer is stored
as a **confirmed** `preference` memory with no source messages — the answers
are the user's own words, so no review step applies. Blank answers are
skipped (`saved` counts only stored rows); the Discover cache is invalidated
when anything is saved. Max 8 answers, 500 chars each.

## Phase 7

The Film Assistant is a **persisted discovery conversation**: the client creates a
`type="discovery"` conversation via `POST /conversations` and turns via
`POST /conversations/{id}/messages`. The server owns the transcript (no
`sessionStorage`), so the chat survives reloads and can be resumed from history;
"End chat" returns to Discover and leaves the conversation active. Each turn
sends `exclude_tmdb_ids` (the films already shown this session) so Regenerate and
follow-up replies rotate to fresh films. The older `/assistant/opening` and
`/assistant/chat` endpoints still exist as stateless helpers (used by tests).

### `POST /assistant/opening` (auth required)
```json
← 200 {"reply": "What are you in the mood for tonight?"}
```
The assistant's first message, built from the user's confirmed memories and
display name. Stateless — no conversation row is created.

### `POST /assistant/chat` (auth required)
```json
→ {"messages": [{"role": "user", "content": "recommend me Thor: Ragnarok"}]}
← 200 {"reply": "…", "recommendations": [
  {"tmdb_id": 284053, "title": "Thor: Ragnarok", "year": 2017,
   "genres": ["Action", "Comedy"], "poster_url": "…", "vote_average": 7.6,
   "runtime": 130, "overview": "…", "themes": []}
]}
→ {"messages": [{"role": "user", "content": ""}]} → 422
```
One stateless turn. The server parses the latest user message for an explicit
constraint (F12): a director ("…by Paul Thomas Anderson"), a named title, or a
genre — each validated against TMDB so only names actually present in the
message are accepted. A constrained request rebuilds the candidate pool around
that ask instead of the generic profile. A film the user names is answered
directly and never refused; if it is already in their library the assistant
acknowledges it ("already in your library — here are films close to it
instead") and returns close alternatives. The reply and `recommendations`
(each a verified film card) are returned together; nothing is persisted.

## Conventions
- Auth: `Authorization: Bearer <supabase access token>`; server verifies JWT.
- Errors: RFC 7807-style `{ "detail": "..." }` with appropriate status codes.
- All list endpoints paginated (`limit`/`offset`); chat context assembly is
  server-side and never exposed raw.
