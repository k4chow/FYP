# 05 — API Reference

Base URL (dev): `http://localhost:8000`. Interactive docs at `/docs` (Swagger,
auto-generated by FastAPI).

## Phase 0

### `GET /health`
Liveness check.
```json
{ "status": "ok", "service": "noacf-api", "version": "0.2.0" }
```

## Phase 1

All auth endpoints are server-mediated (D9): the client only talks to
FastAPI; the server uses the Supabase service-role key. Signup/login return
a Supabase JWT that the client sends as `Authorization: Bearer <jwt>`.

### `POST /auth/signup`
```json
→ {"email": "a@b.com", "password": "min8chars", "display_name": "Kiwi"}
← 200 {"access_token": "<jwt>", "user": {"id": "...", "email": "...", "display_name": "Kiwi"}}
```
Creates the Supabase Auth user (auto-confirmed in dev — no SMTP configured)
and the `public.users` profile row, then logs in and returns the session.

### `POST /auth/login`
```json
→ {"email": "a@b.com", "password": "..."}
← 200 {"access_token": "<jwt>", "user": {...}}
← 401 {"detail": "Invalid email or password"}
```

### `POST /auth/forgot-password`
```json
→ {"email": "a@b.com"}
← 200 {"message": "If that email exists, a reset link has been sent."}
```
Same response whether or not the account exists (no user enumeration).
Requires SMTP configured in Supabase to actually deliver.

### `GET /auth/me`
```json
← 200 {"id": "...", "email": "...", "display_name": "Kiwi"}
← 401 {"detail": "Invalid or expired token"}
```
Self-heals the `public.users` profile row if it is missing.

### `POST /auth/change-password` (added Phase 2, auth required)
```json
→ {"current_password": "...", "new_password": "min8chars"}
← 200 {"ok": true}
← 400 {"detail": "Current password is incorrect"}
```
Verifies the current password (via a sign-in attempt) before updating.

## Phase 2

TMDB access is server-side only (`server/app/tmdb.py`) so the API key never
reaches the client; the `films` table caches fetched metadata. `poster_url`
values are absolute URLs against the TMDB image CDN.

### `GET /films/search?q=`
```json
← 200 {"results": [{"tmdb_id": 329865, "title": "Arrival", "year": 2016,
                    "poster_url": "https://image.tmdb.org/t/p/w342/…", "overview": "…"}]}
```
Top 8 TMDB results.

### `GET /films/tmdb/{tmdb_id}`
```json
← 200 {"tmdb_id": 329865, "title": "Arrival", "year": 2016,
       "genres": ["Drama", "Science Fiction", "Mystery"], "runtime": 116,
       "overview": "…", "poster_url": "…",
       "in_library": {"id": "…", "status": "watched", "rating": 4.5} | null}
← 404 {"detail": "Film not found on TMDB"}
```

### `GET /films/mine?status=watched|watchlist`
```json
← 200 {"films": [{"id": "<user_film id>", "film_id": "…", "tmdb_id": 329865,
                  "title": "Arrival", "year": 2016, "genres": ["Drama", …],
                  "runtime": 116, "poster_url": "…",
                  "status": "watched", "source": "manual|letterboxd",
                  "rating": 4.5 | null, "watched_on": "2026-10-20" | null,
                  "added_at": "…"}]}
```
Ordered by `added_at` desc; optional `status` filter.

### `POST /films/mine`
```json
→ {"tmdb_id": 329865, "status": "watched", "rating": 4.5, "watched_on": "2026-10-20"}
← 201 {<user_film row + film fields>}
```
`rating`/`watched_on` optional. Fetches + caches TMDB metadata on first sight
of a film; upserts on `unique(user_id, film_id)` so re-adding updates status.

### `PATCH /films/mine/{user_film_id}`
```json
→ {"status": "watchlist", "rating": 4.0, "watched_on": "2026-10-20"}   (any subset)
← 200 {"ok": true}   ← 404 if the row is not the caller's
```

### `DELETE /films/mine/{user_film_id}`
```json
← 200 {"ok": true}   ← 404 if the row is not the caller's
```

### `POST /import/letterboxd` (multipart form, field `file`)
```json
← 200 {"total_rows": 6, "matched": 5,
       "unmatched": [{"name": "Notarealfilm Xyzqw", "year": 2099}]}
← 400 {"detail": "Not a Letterboxd export CSV — …"}
```
Accepts `diary.csv`, `ratings.csv`, `watched.csv`, `watchlist.csv` (any file
with `Name`+`Year` columns). Status is `watchlist` when the filename contains
"watchlist", otherwise `watched`. Rows are matched catalogue-first, then TMDB
title+year (first result; title-only fallback), upserted with
`source='letterboxd'` — re-importing updates ratings and never duplicates.

## Phase 3

Reflection and discovery chat. `LLM_PROVIDER=mock` selects the deterministic
provider (no API key); every user and assistant message, including the opening,
is stored verbatim in `messages` (D11). All routes require auth and are scoped
to the caller. A conversation's `film` is `null` or contains
`id/tmdb_id/title/year/genres/runtime/overview/poster_url`.

### `POST /conversations`
```json
→ {"type": "reflection", "tmdb_id": 329865, "watch_type": "seen"}
← 201 {"conversation": {"id": "…", "type": "reflection", "status": "active",
       "watch_type": "seen", "title": "Reflection on Arrival",
       "created_at": "…", "updated_at": "…", "ended_at": null, "film": {...}},
       "messages": [{"id": "…", "role": "assistant", "content": "…",
                     "metadata": {"kind": "opening"}, "created_at": "…"}]}
```
Use `film_id` for an existing catalogue row or `tmdb_id` to fetch/cache it.
`type` defaults to `reflection`; `watch_type` is optional `seen|planning` but
requires a film (400 otherwise). For a film-free prompt reflection send
`{"type":"reflection","title":"What film character would you want as a friend?"}`.
The response includes the persisted assistant opening.

### `GET /conversations?status=active|completed&type=reflection|discovery`
```json
← 200 {"conversations": [{<conversation with film>}…]}
```
Ordered by `updated_at` desc; both filters are optional.

### `GET /conversations/{id}`
```json
← 200 {"conversation": {<conversation with film>},
       "messages": [{"id": "…", "role": "assistant|user",
                     "content": "…", "metadata": {}, "created_at": "…"}…]}
← 404 {"detail": "Conversation not found"}
```
Messages are chronological. Full history is returned for display; only the LLM
context is bounded (last 12 messages + 5 confirmed memories by default).

### `POST /conversations/{id}/messages`
```json
→ {"content": "I loved the quiet atmosphere and the way it handled grief."}
← 201 {"user_message": {<stored message>}, "assistant_message": {<stored message>}}
← 409 {"detail": "This conversation has ended"}
```
Stores the user message verbatim, assembles bounded context, generates and
stores the assistant reply, and touches the conversation's `updated_at`.
Content is required (1–4000 chars).

### `POST /conversations/{id}/end`
```json
← 200 {"conversation": {<conversation>, "status": "completed",
                       "ended_at": "2026-11-03T…"}}
```
Idempotent. Phase 4 adds proposed-memory extraction to this endpoint; it never
auto-confirms memories (D12).

## Conventions
- Auth: `Authorization: Bearer <supabase access token>`; server verifies JWT.
- Errors: RFC 7807-style `{ "detail": "..." }` with appropriate status codes.
- All list endpoints paginated (`limit`/`offset`); chat context assembly is
  server-side and never exposed raw.
