# 03 — Design Decisions

Each entry: decision → alternatives considered → rationale. Written to be
reusable as thesis justification material.

| # | Decision | Alternatives | Rationale |
|---|---|---|---|
| D1 | React + Vite + TypeScript client | Next.js, Vue | Team familiarity (same structure as previous project); Vite is fast and minimal; no SSR requirement |
| D2 | FastAPI server | Node/Express, Django | Python ecosystem for LLM/ML work; async-first; automatic OpenAPI docs; already installed in dev environment |
| D3 | Supabase Postgres | Self-hosted Postgres, Firebase, MongoDB | Managed Postgres with built-in Auth, RLS for per-user data isolation, generous free tier, SQL familiarity |
| D4 | Relational schema, JSONB only for flexible metadata | Full JSONB documents | Queryability and integrity for core entities; JSONB reserved for genuinely variable data (`metadata`, `source_message_ids`) |
| D5 | Mock LLM provider behind an interface | Direct OpenAI integration from day 1 | No key available yet; deterministic mock makes every flow testable and demos reproducible; swap is one class |
| D6 | Letterboxd CSV import only | Netflix/IMDb import, manual entry only | Notes scoped it this way; Letterboxd export is a clean documented CSV; avoids scope creep |
| D7 | TMDB for film metadata | OMDb, IMDb scraping | Free API key, good coverage, poster CDN, stable API |
| D8 | pgvector deferred | Adopt pgvector from Phase 0 | Notes explicitly say add it only if plain SQL retrieval is insufficient — avoids premature complexity |
| D9 | Server-mediated DB access (not direct client→Supabase) | Client talks to Supabase directly | Single place to enforce memory lifecycle and context assembly; RLS still enabled as defence in depth |
| D10 | Monorepo (`client/` + `server/` + `supabase/`) | Separate repos | FYP scale; one commit history maps cleanly onto phases; mirrors previous project structure |
| D11 | Append-only messages; derived profile in separate table | In-place summarisation of history | Source of truth must be auditable; enables "why am I seeing this" traceability via `source_message_ids` |
| D12 | Proposed→confirmed memory lifecycle | Auto-save insights | Central requirement: the user owns their reflective profile; auto-saving would undermine trust |
| D13 | Dev accounts auto-confirmed (`email_confirm: true` on signup) | Require email verification from day 1 | No SMTP configured in the dev Supabase project; mandatory verification would block all testing. Must be switched on before any public deployment |
| D14 | Two Supabase clients: `supabase` (DB only) + `auth_client` (auth API only) | Single shared client; raw REST auth calls | supabase-py propagates sign-in state into the client's PostgREST headers, silently downgrading later DB calls from service-role to a user JWT (surfaced as an RLS 500 on `films` upsert during Phase 2). Separate instances make the correct behaviour structural, not order-dependent |
| D15 | Import matching: local catalogue first, then TMDB title+year first result (title-only fallback); upserts make re-import idempotent; unmatched rows reported, not dropped | Fuzzy matching; per-row manual review UI (as in the onboarding mockup) | Deterministic and explainable for thesis evaluation; catalogue-first avoids repeat TMDB calls; the mockup's review-before-confirm step is deferred to the onboarding flow (Phase 5), keeping the Settings/Import path simple |
| D16 | The assistant's opening message is persisted as the first `messages` row | Client-injected placeholder; system prompt only | Chat history has one source of truth from the first render; opening messages remain auditable and appear in every later reload |
| D17 | Store `watch_type` as `seen` \| `planning`; the mockup's “First time watching” / “Rewatch” choice is UI-only framing | Four stored states; no watch context | Seen/planning is the distinction that changes the assistant's questions; first-watch versus rewatch can be added later if it proves useful without complicating the initial contract |
| D18 | Bounded context defaults to the last 12 messages + 5 most recently updated confirmed memories, configurable via settings | Full history; hard-coded limits | Makes F4 explicit and testable; keeps prompt cost predictable while allowing evaluation with different window sizes |
| D19 | Ending a conversation is idempotent; posting to a completed conversation returns 409 | 409 on duplicate end; allow post-completion messages | Double-clicks and retries are safe; completed reflections remain stable for the Phase 4 review flow |
| D20 | Letterboxd imports are persistent background jobs with per-row outcomes and batch checkpoints | One long synchronous request; client-only progress | A 1,600-row import needs thousands of external calls; one timeout or TMDB error must not strand a partial library with no recovery path. Queued/processing jobs are recovered on startup and failed rows can be resumed |
| D21 | Import jobs store only normalized resume fields + outcomes, never the original CSV | Store the uploaded file or every CSV column | Resume needs name/year/rating/watched date only; minimizing retained data is safer and keeps the job table small. Duplicates mean repeat CSV rows or already-current library rows; transient failures are distinct from unmatched titles |
| D22 | TMDB 429/network/upstream retries use bounded exponential backoff with jitter (4 attempts max) | Unlimited retries; one fixed-delay retry; larger HTTP timeouts | Transient failures are isolated to one film and remaining rows continue; bounded jittered retries avoid hammering TMDB without hiding architectural problems |
| D23 | Reflection linkage for memories is derived from validated `source_message_ids`, not a parallel insight table or redundant profile model | New insight table; store a duplicate conversation foreign key now | The existing `memories` schema remains the user-controlled layer-2 model; source ids give finer provenance and remain unchanged across edits, while the API resolves the owned conversation for review screens |
| D24 | Extraction uses the same bounded message window as chat, returns at most three mock proposals, and the server validates kind/content/explanation/source ids before insert | Full-history extraction; trust provider JSON | Preserves F4's cost/privacy boundary, produces a reviewable set instead of one row per message, and malformed provider output cannot create invalid rows |
| D25 | Review transitions are only `proposed → confirmed` or `proposed → rejected`; text edits are saved with confirmation | Free editing in any status; automatic confirmation | Keeps D12 explicit: no generated wording becomes profile memory until the user keeps it, while confirmed/rejected rows are stable audit outcomes |
| D26 | The PostgREST transport runs HTTP/1.1 with keep-alive pooling disabled (fresh connection per query) | postgrest default session (HTTP/2 + pooled keep-alive); application-level retry wrappers around every DB call | The dev network path (local proxy/NAT) silently breaks h2 and idle pooled connections — the same reason git push needs `http.version=HTTP/1.1` — surfacing as intermittent `RemoteProtocolError` 500s across unrelated endpoints. One transport configuration in `supabase_client.py` removes the failure class for every query without scattering retry logic through the routers; the small per-request TLS cost is acceptable in dev |
| D27 | Mock provider questions come from a curated prompt bank (openers / follow-ups / deeper questions), sampled without immediate repetition per session; the RNG is injectable (`MockLLMProvider(rng=...)`) so tests are deterministic | Fixed question sequence; free-form generated questions | A fixed sequence made every reflection feel identical; the bank keeps the mock honest and varied while seeded RNG keeps behaviour assertable in tests. Bank documented in `server/app/llm/mock.py` |
| D28 | Watched always wins: imports and manual adds never downgrade an existing `watched` row to `watchlist` (a watchlist hit on a watched row is counted as a duplicate no-op); a `watchlist` row is upgraded by any watched signal | Last-write-wins upsert; block re-adding | Importing `watchlist.csv` after `watched.csv` (or vice versa) silently flipped statuses under plain `on_conflict` upsert; the rule is enforced server-side in both `import_jobs` and `POST /films/mine`, with regression tests for both orders plus the manual path |
| D29 | Confirmed memories remain editable and rejectable from My Profile (confirmed → confirmed re-edit, confirmed → rejected retraction); only `rejected` is terminal | Freezing confirmed rows; allowing resurrection of rejected rows | D12 says the user owns the profile — ownership does not end at confirmation. `source_message_ids` survive every edit; rejected rows stay as audit trail |
| D30 | Onboarding completion is a flag on the `users` profile row (`onboarding_completed`, migration 0004), checked by the client router; new signups default to `false`, existing accounts are grandfathered to `true` | Client-local storage flag; a separate onboarding table | Per-device flags would re-onboard the same user on every new browser; a server flag survives sign-out/sign-in and keeps existing users out of the flow. Every onboarding step is skippable, and skipping also marks the flag complete |
| D31 | A third Supabase client, `admin_auth_client`, is dedicated to admin auth calls (`create_user` / `update_user_by_id` / `delete_user`) and never performs a sign-in | Reusing `auth_client` for both sign-in and admin calls; constructing a fresh client per request | gotrue-py persists sign-in state on the client, so after `sign_in_with_password` the client's Authorization header carries the signed-in user's JWT and subsequent admin calls fail with `User not allowed` (or `token is expired` once it lapses) - surfaced when the Phase 5 E2E ran signups after earlier logins. The split makes D14's isolation complete: DB client, user-facing auth client, admin auth client |

| D32 | Import matching is year-strict: when a Letterboxd row has a year, a TMDB title-only fallback result is only accepted if its release year matches; otherwise the row is reported unmatched, never guessed | Always taking the first title-only result (D15's original fallback) | Title-only first results are ranked by popularity, so a failed title+year lookup silently imported the most popular same-title film (usually a remake) alongside the intended one on re-import — different `film_id`s, so `unique(user_id, film_id)` could not catch it. Unmatched rows surface in the import report where the user can see them. A dry-run cleanup tool (`server/scripts/cleanup_duplicate_films.py`) reconciles historical same-title pairs against the years in the user's stored import rows |
| D33 | The first real LLM provider is OpenAI (`server/app/llm/openai.py`), selected with `LLM_PROVIDER=openai`; key via `OPENAI_API_KEY`, model via `OPENAI_MODEL` (default `gpt-4o-mini`) | Hard-wiring the SDK into routers; committing the key to `.env.example` | Keeps D5's seam: routers still only call `get_llm()`. The key lives in gitignored `.env` locally and in the hosting platform's env settings on deploy — never in the repo or the client bundle. Insight extraction requests JSON mode and unparseable output raises so the conversation stays active for a retry instead of ending with no proposals |
| D34 | `getMyFilms` dedupes accumulated pages by row id | Server-side cursor pagination; no dedupe | Pages are ordered by `added_at` desc; while an import is running, new rows prepend and shift every later page window, so the same card rendered repeatedly (the "Greatest Showman x8" report — the database held exactly one row). Client-side id-dedupe removes the whole visible-duplicate class without changing the API; offsets still advance by raw page size so ranges stay aligned |

| D35 | The recommendation engine is deterministic SQL+TMDB scoring, not embeddings or LLM ranking: seeds (explicit "more like this" feedback, then ≥4★ rated and watchlisted films) each pull TMDB `/movie/{id}/recommendations`, a `/discover/movie` pool covers the library's top genres, and candidates score as `seed_score × (0.5 + similarity) + memory_bonus + explore_bonus` where `similarity = 1 − style/100` | pgvector semantic search; asking the LLM to pick films; collaborative filtering | Keeps D8's pgvector deferral: every signal is already relational, results are reproducible for the same inputs (tested), and every score component maps to a visible explanation. Memory affinity is keyword/genre-alias matching against confirmed memories only (D12), capped at three memories per card. Cold start (empty library) falls back to popular TMDB picks with an honest why-line |
| D36 | Recommendation feedback lives in `recommendation_feedback (user_id, tmdb_id, title, signal)` with `unique(user_id, tmdb_id)`, upsert semantics, and the film title denormalised onto the row | Feedback as a memory kind; a join back to `films` for titles | "Not for me" films are hard exclusions and "more like this" films become the strongest seeds on the next run — the loop must be immediate and cheap. The title is stored so "Because you asked for more like X" never needs an extra TMDB details call; recommended films are not cached in `films` until actually added to a library. Both feedback posts and style changes invalidate the per-user 5-minute result cache |
| D37 | The style slider persists as `users.recommendation_style smallint (0–100, default 30)` via `GET/PATCH /profile/preferences` | A separate preferences table; client-local storage | One scalar weighting one formula term (and the exploration bonus) does not justify a table; server-side persistence keeps the slider consistent across devices (same reasoning as D30's onboarding flag). The 0–100 range is validated by a check constraint and the endpoint |
| D38 | Onboarding runs import → library picks → one-film first reflection → about-you questionnaire; questionnaire answers are user-authored, so they are stored directly as **confirmed** preference memories (`POST /profile/questionnaire`, no review step) | Questionnaire before the first reflection (Phase 5's original order); answers as proposed memories awaiting review | The reflection is more grounded once the library has films in it, and the questionnaire works better as a follow-up ("now tell us about you") than a gate. D12's review step exists to protect users from system inference — data the user typed about themselves is already user-controlled, so forcing review would add friction without adding protection. Sourceless confirmed memories explain themselves as "You wrote this about yourself." |

## UI variation decisions (from mockup review)

| Screen | Chosen | Rejected | Why |
|---|---|---|---|
| Home | Full sidebar dashboard (screen 15) | 4 minimal layout options (16) | Most complete; consistent with the shell every other screen uses; options in 16 are subsets of it |
| Review & edit insights | Richer version (12) | Simplified restyle (13) | Adds "themes to add to your profile" and "Why am I seeing this?" — both required features |
| Add a Reflection | Hybrid: browse sections of 21 + selected-film bottom bar of 22 | Centered search-first layout (20) | Best interaction model: browse when unsure, explicit watch-type + CTA once a film is chosen |
| Reflection chat | Layout with End reflection button (11) | Variant without it (09) | "End reflection" is required to trigger the guided review flow; keeps 09's quick-reply chips |
| "What catches your attention" (07) | Repurposed into reflection-start flow | Use in onboarding | User annotation: "might be too cluttered" for onboarding; cleaner entry-points screen (10) covers the first reflection |
